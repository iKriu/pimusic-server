# Фаза 2: эквалайзер и фишки плеера, вход вне Telegram, PWA → приложения Windows/Android

Контракт между бэкендом (`bot/app/*.py`), Mini App (`bot/app/static/`) и нативными приложениями (`apps/`).
Дизайн: `design/DESIGN.md` (M3 Expressive, русский UI). Предыдущий контракт: `design/PLAYER_API.md`.

## A. Бэкенд
1. **Синхронный текст**: `GET /api/lyrics/{track_id}` → `{"synced": [{"t": 12.34, "text": "…"}…] | null,
   "plain": "…" | null, "source": "lrc"|"tags"|null}`. Источник — `.lrc`/`.txt` рядом с файлом
   (ссылка пользователя или кэш) или USLT-тег. Доступ — как у потока (`track_access`). Разбор LRC с
   `[mm:ss.xx]`, несколько меток на строку, `[offset:]`. Кэш в памяти по (track_id, mtime).
2. **Громкость (ReplayGain)**: колонка `tracks.gain_db REAL`, `tracks.peak REAL`. Фоновый анализ
   ffmpeg `ebur128` (или `loudnorm print_format=json`) — по одному треку, низкий приоритет (`nice`),
   новые треки после загрузки + досчёт старых в фоне. Цель −14 LUFS (gain = −14 − I), peak из true peak.
   В JSON трека (`_lib_item`): `"gain": -3.2, "peak": 0.98` (null если не посчитано). Если в файле есть
   теги REPLAYGAIN_TRACK_GAIN — брать их.
3. **Настройки пользователя (синхронизация между устройствами)**: `GET /api/settings` → `{"eq": {...},
   "player": {...}, "updated_at": …}`; `POST /api/settings` `{"eq"?:…, "player"?:…}` — JSON до 16 КБ,
   хранится как есть (таблица `user_settings(login PK, data TEXT, updated_at)`), сервер не интерпретирует.
4. **Вход вне Telegram (PWA, Windows, Android)** — токены устройств:
   - `POST /api/auth/start` (без авторизации, rate limit по IP) → `{"nonce": "…", "link":
     "https://t.me/<bot>?start=login_<nonce>", "expires_in": 300}`.
   - Бот `/start login_<nonce>` → сообщение «Войти в PiMusic на новом устройстве?» с кнопками
     «Разрешить»/«Отклонить» (показывать тип устройства из `device` при start). Разрешить → nonce привязан к логину.
   - `POST /api/auth/poll {"nonce"}` → `{"status": "pending"|"denied"|"expired"}` или
     `{"status":"ok","token":"…","login":"…"}` (токен выдаётся один раз).
   - Также **Telegram Login Widget**: `POST /api/auth/telegram {…поля виджета, hash}` — проверка по
     https://core.telegram.org/widgets/login#checking-authorization (secret = SHA256(bot_token)), auth_date ≤ 1 сутки.
     Требует `/setdomain` у BotFather — описать в README, фронтенд показывает виджет только если сервер
     сообщил `login_widget: true` (`GET /api/auth/config` → `{"bot": "<username>", "login_widget": bool}`).
   - Токен: `secrets.token_urlsafe(32)`, в БД только SHA-256; таблица `devices(id, login, name, platform,
     token_hash UNIQUE, created_at, last_seen)`. API принимает `Authorization: Bearer <token>` наравне с
     initData. `GET /api/devices`, `POST /api/devices/{id}/revoke`, `POST /api/auth/logout`.
     В боте `/devices` — список и отзыв. Ограничение 20 устройств на пользователя.
   - CORS: для `/api/*` разрешить Origin из списка (`tauri://localhost`, `http://tauri.localhost`,
     `https://tauri.localhost`, `capacitor://localhost`, `http://localhost`, `https://localhost`) с заголовками
     Authorization/Content-Type; поток `/api/stream` и обложки — тоже (Range, Accept-Ranges, Content-Range в expose).
5. Тесты на всё (pytest, существующие фикстуры).

## B. Mini App / PWA (static/)
1. **Эквалайзер** (Web Audio, на общем `<audio>` очереди):
   - 10 полос `BiquadFilterNode` (peaking; крайние можно переключить в lowshelf/highshelf), по умолчанию
     31, 62, 125, 250, 500, 1k, 2k, 4k, 8k, 16k Гц; у каждой полосы вручную: частота (20–20000, лог-шкала),
     усиление (−12…+12 дБ, шаг 0.5), Q (0.3–8); преамп (−12…+6 дБ); вкл/выкл (bypass); сброс.
   - Кривая АЧХ на canvas (getFrequencyResponse суммарно), перетаскивание точек полос по кривой
     (x — частота, y — усиление, колесо/щипок — Q), доступные слайдеры как альтернатива (role=slider).
   - Пресеты: встроенные (Ровно, Бас+, Высокие+, Вокал, Рок, Электроника, Классика, Подкаст, Наушники-тёплые,
     Громкость ночью) + свои (сохранить/переименовать/удалить), A/B сравнение (быстрый bypass).
   - Анализатор спектра поверх кривой (опционально, выкл. под reduced motion).
   - Лимитер/компрессор на выходе (DynamicsCompressor) от клиппинга при подъёме полос.
   - Хранение: localStorage + синхронизация через `/api/settings` (последний выигрывает по updated_at).
   - Режим «волна» тоже идёт через EQ (тот же граф). iOS: EQ по умолчанию выключен с пояснением
     (фоновое воспроизведение может прерываться при включённом Web Audio), включается вручную.
2. **Фишки плеера**: нормализация громкости по `gain/peak` (вкл/выкл, режим трек), плавный переход
   (crossfade 0–12 с, два `<audio>` и GainNode-рампы; gapless при 0), таймер сна (15/30/45/60 мин,
   «до конца трека», плавное затухание), скорость 0.5–2× (preservesPitch), синхронный текст в «Сейчас играет»
   (подсветка строки, автопрокрутка, тап по строке = перемотка; без синхронного — обычный текст).
3. **Где в UI**: «Сейчас играет» → кнопки «Текст», «Эквалайзер» (полноэкранный лист/правая панель на
   широких), меню ⋮ → «Таймер сна», «Скорость», «Плавный переход», «Нормализация громкости».
   Раздел «Настройки» (из меню профиля) со всем этим + «Устройства» (список, отзыв).
4. **PWA и вход вне Telegram**: `manifest.webmanifest` (иконки 192/512/maskable, theme/background из токенов,
   display standalone, shortcuts «Моя Волна», «Поиск»), service worker (кэш оболочки app shell, офлайн-экран;
   НЕ кэшировать /api и поток), регистрация только вне Telegram. Если нет `Telegram.WebApp.initData` —
   экран входа M3E: «Войти через Telegram» (deep-link flow: открыть ссылку, опрос `/api/auth/poll` каждые 2 с,
   QR-код ссылки для входа с другого устройства) и, если сервер разрешил, виджет Telegram Login.
   Токен в localStorage, `api.js` шлёт `Authorization: Bearer`. Выход, обработка 401 (снова экран входа).
   Код платформы (`platform`: web/pwa/windows/android) — для списка устройств.
5. M3E-полировка и доступность плеера (по ревью интерфейса).

## Дополнение (пользователь): синхронизация EQ и пресеты по устройствам
- **Библиотека пресетов** (встроенные + свои) — общая, синхронизируется на все устройства.
- **У каждого устройства свой режим**: «Синхронизировать» (устройство следует общему активному профилю — меняешь
  на одном, меняется везде, где включена синхронизация) или «Только это устройство» (свой активный пресет и свои
  ручные полосы, не влияют на другие и не меняются от них). Переключатель режима — в эквалайзере, наверху.
- **Устройство**: стабильный id в localStorage (uuid), имя по умолчанию из платформы («Telegram · Android»,
  «Windows», «Браузер · iPhone»…), переименовываемое; в «Настройки → Устройства» видно, какой пресет/режим у
  каждого устройства, и можно изменить EQ другого устройства удалённо (например, настроить ТВ-приставку с телефона).
- Возможно, позже: автоматическое переключение по выходу звука (наушники/динамик) — браузеры это надёжно не
  сообщают, поэтому не делаем, но держим структуру данных готовой (профиль на устройство).
- **Хранение на сервере — по ключам, чтобы устройства не затирали друг друга**:
  `GET /api/settings` → `{"items": {"<key>": {"value": …, "updated_at": …}}}`;
  `PUT /api/settings/<key>` `{"value": …, "base"?: updated_at}` (если `base` устарел → 409 с актуальным значением);
  `DELETE /api/settings/<key>`. Ключи: `eq.presets` (общая библиотека), `eq.shared` (общий активный профиль),
  `eq.device.<deviceId>` (`{name, platform, mode: "sync"|"local", active, bands, preamp, enabled}`), `player`.
  Ключ ≤ 80 символов `[a-z0-9._-]`, значение ≤ 32 КБ, ≤ 100 ключей на пользователя. Устаревший вариант
  `POST /api/settings` целиком — не нужен (заменяется этим).

## D. Загрузка своих файлов (пользователь, 2026-10-18)
Пользователь сам загружает аудиофайлы; тегирование всё равно делает сервер.
**Бэкенд**
- Источники: (1) бот — аудио/документ/несколько файлов (лимит Bot API на скачивание 20 МБ — сообщать понятно,
  предлагать Mini App для больших); (2) Mini App — `POST /api/upload` multipart (поток на диск, до 300 МБ на файл,
  до 50 файлов за раз; mp3, flac, wav, m4a/aac, ogg/opus, wma? — что умеет ffmpeg), ответ `{"uploads":[{id, name, state}]}`.
- Таблица `uploads(id, login, orig_name, path, state, guess_artist, guess_title, track_id, note, created_at)`;
  состояния: `queued → analyzing → need_info → processing → done | duplicate | failed`. Переживает перезапуск.
- Конвейер (отдельный воркер, 1–2 параллельно): проверка ffprobe (это аудио, длительность) → нормализация в
  MP3 CBR 320 (lossless/другие форматы — перекодировать; mp3 — оставить как есть, без «апскейла», но
  отметить битрейт) → опознание: существующие теги → **AcoustID** (fpcalc/chromaprint, если есть ключ
  `ACOUSTID_API_KEY` в .env; без ключа — пропустить) → MusicBrainz/iTunes по тегам/имени файла (тот же tagger, что
  для загрузок, с проверкой длительности) → если уверенности нет — `need_info`.
- `need_info`: бот пишет «Не смог опознать «<файл>» (3:42). Пришлите «Исполнитель — Название»» (ForceReply,
  кнопки «Оставить как есть» = сохранить с тем, что есть/имя файла, «Отмена»); Mini App: `GET /api/uploads`,
  `POST /api/uploads/{id}/info {"artist","title","album"?}`, `POST /api/uploads/{id}/skip|cancel`. После ответа
  сервер сам ищет метаданные по подсказке (обложка 1000×1000, синхронный текст, ReplayGain) и кладёт в общий кэш.
  В сети обложки или текста нет — берутся свои из файла (ID3, FLAC, MP4), приведённые к виду сервера: JPEG
  до 1000×1000, USLT/SYLT и `.lrc`/`.txt`; синхронный текст — только если метки укладываются в длину трека.
- Ручная загрузка главнее скачанного: тот же ISRC/MBID/запись уже в кэше → загруженный файл заменяет файл трека
  у всех держателей (`done`, `note` «заменил прежний файл трека»; дубля в кэше нет, трек появляется в медиатеке).
  Скачанный из сети файл загруженный не вытесняет — только «Перекачать трек» или повторное скачивание этого трека
  отдельно. `duplicate` остаётся в списке состояний для старых записей. Уведомления в бот о результате
  (группировать при пачке файлов).
- Безопасность: проверка, что это аудио (ffprobe), имена файлов не используются как пути, лимиты на размер/
  количество/диск (не принимать, если свободно < 5 ГБ), временная папка в incoming/uploads, чистка мусора.
**Mini App**
- Кнопка «Загрузить файлы» (Загрузки и Медиатека): выбор файлов/перетаскивание, прогресс загрузки по файлам
  (XHR upload progress), список загрузок с состояниями; карточка `need_info` с формой «Исполнитель / Название /
  Альбом (необяз.)», подсказками из имени файла и кнопками «Сохранить», «Оставить как есть», «Отмена».

## Изменения бэкенда (фаза 2)
Раздел A реализован; уточнения и отклонения (обратно совместимо с текстом выше):
- **Текст** `/api/lyrics/{id}`: порядок поиска — `.lrc` рядом со ссылкой пользователя, `.lrc` в кэше, `.txt`
  (оба места), затем USLT-тег. Для `.txt` `source` = `"lrc"` (это файл-спутник). Синхронным считается текст, где
  ≥ 3 строк с метками; `plain` у синхронного — тот же текст без меток. Нет доступа / нет трека — 404.
- **Громкость**: `gain`/`peak` в JSON трека округлены до 0.01 дБ / 0.0001; `gain` ограничен −30…+20 дБ.
  Теги REPLAYGAIN_TRACK_GAIN (ReplayGain 2.0, опора −18 LUFS) пересчитываются к −14 LUFS (+4 дБ).
  Анализ один раз на трек (неудача не повторяется); если в ffmpeg нет `ebur128`/`loudnorm` — анализ выключается
  без пометок, треки досчитаются после обновления образа. Выключатель: `LOUDNESS_ANALYSIS=false`.
- **Настройки** (по ключам, раздел «Дополнение»): `updated_at` — **миллисекунды**, строго растёт по ключу.
  `PUT /api/settings/<key>` → `{"key","value","updated_at"}`; `409 {"error":"conflict","current":{value,updated_at}|null}`
  (`base` для несуществующего ключа — тоже конфликт, `current: null`); `409 limit` (100 ключей), `413 too_large`
  (> 32 КБ), `400 bad_key|bad_value|bad_base|bad_json`. `DELETE` → `{"ok":true,"deleted":bool}`.
  Старого `POST /api/settings` нет.
- **Вход**: `POST /api/auth/start` принимает необязательное тело `{"device": "<имя ≤64>", "platform":
  "web|pwa|windows|android|ios|linux|macos"}` (иначе `web`) — это показывается в боте. 10 запросов за 10 минут на IP
  (`X-Forwarded-For` учитывается только от адресов локальной сети; берётся самый правый публичный адрес) → `429 rate_limited`.
  `link` = null, если имя бота ещё неизвестно. `POST /api/auth/poll`: неизвестный/использованный/истёкший nonce →
  `expired`; неверный формат → 400. Токен выдаётся только первому опросу после «Разрешить», в течение 5 минут от start.
- **Виджет**: `POST /api/auth/telegram` — поля виджета как есть + необязательные `device`, `platform` (в подпись не
  входят). Ответ `{"status":"ok","token","login"}`; ошибки `401 unauthorized` (подпись/срок), `403 not_registered`,
  `404 disabled` (нет `LOGIN_WIDGET=true`), 429. `GET /api/auth/config` → `login_widget` true только при
  `LOGIN_WIDGET=true` и известном имени бота.
- **Устройства**: `GET /api/devices` → `{"items":[{id,name,platform,created_at,last_seen,current}]}` (`current` — это
  устройство, если вошли по Bearer). `POST /api/auth/logout` → `{"ok":true,"revoked":bool}` (при входе через initData
  отзывать нечего). Лимит 20: при 21-м входе удаляется устройство, дольше всех не появлявшееся (а не отказ).
  `last_seen` обновляется не чаще раза в минуту. Неверный/отозванный Bearer → `401 unauthorized`.
- **CORS**: методы `GET, POST, PUT, DELETE, OPTIONS`; заголовки `Authorization, Content-Type, Range,
  X-Telegram-Init-Data`; expose `Content-Range, Accept-Ranges, Content-Length, Content-Type`; доп. Origin —
  `CORS_ORIGINS` в .env. Чужой Origin — без CORS-заголовков. Только `/api/*`.
- **D. Загрузки (бэкенд)** — реализовано; уточнения:
  - `POST /api/upload` (multipart/form-data, любое имя поля с файлом; поля без файла пропускаются) →
    `{"uploads":[{id,name,state:"queued"}], "rejected":[{name, error, message}]}`; `error`: `bad_type` (расширение
    не из списка аудио), `too_large` (> `UPLOAD_MAX_MB`), `empty`, `too_many` (> 50 за запрос или > 200 в очереди
    у пользователя), `disk_full` (свободно < `UPLOAD_MIN_FREE_GB`). Без файлов → `400 no_files`, не multipart →
    `400 bad_multipart`. Имена `%XX` (так кодирует часть клиентов) раскодируются.
  - `GET /api/uploads` → `{"items":[{id,name,state,state_text,artist,title,album,duration,size,note,created_at,
    updated_at,track}]}` (последние 100; `track` — трек как в медиатеке, для `done`/`duplicate`).
    Состояния: дополнительно `receiving` (файл ещё принимается из Telegram) и `cancelled`.
  - `POST /api/uploads/{id}/info {"artist","title","album"?}`, `…/skip`, `…/cancel` → загрузка (как в списке);
    `409 bad_state` (например, уже обрабатывается), `404` — чужая/нет. `cancel` — только `queued`/`need_info`.
  - В боте вопрос — сообщение с кнопками «Оставить как есть»/«Отмена»; ответ — **реплаем** на это сообщение
    «Исполнитель — Название[ — Альбом]» (ForceReply и кнопки в одном сообщении Telegram не допускает).
  - Итог пачки — одним сообщением, когда все файлы пачки обработаны или ждут названия; решённые позже — отдельной
    строкой. Загрузки из Mini App сообщают итог в личный чат с ботом, вопросы «need_info» — только в Mini App.
  - MP3 любого битрейта не перекодируется (`note`: «MP3 128 kbps — сохранён без перекодирования»).
  - «need_info» дольше 14 дней отменяются; файлы без записи в базе в `incoming/uploads` удаляются через сутки.
  - AcoustID: `fpcalc` или ffmpeg с chromaprint (`-f chromaprint`); в образе бота сейчас нет `fpcalc` —
    без него шаг пропускается (см. отчёт).

## Вопросы фронтенда (фаза 2)
1. **Service worker**: чтобы PWA работала офлайн-оболочкой, `static/sw.js` нужно отдавать ещё и как `/app/sw.js`
   (`Content-Type: text/javascript`, `Cache-Control: no-cache`) — scope SW не может быть шире его пути. Клиент сначала
   проверяет `/app/sw.js` (HEAD), иначе регистрирует `static/sw.js` (кэш только статики).
2. **«Выйти на всех устройствах»**: клиент шлёт `POST /api/auth/logout {"all": true}`, затем отзывает остальные
   `/api/devices/{id}/revoke` по одному — если появится отдельный эндпоинт, достаточно поддержать `all`.
3. **401**: клиент различает `error` = `revoked` / `token_expired` (иначе общий текст) и показывает экран входа.
4. **Вход**: поле `code` из `/api/auth/start` показывается крупно («Код подтверждения»); `denied` → «Попробовать снова» с новым nonce.

- `POST /api/auth/start` → дополнительно `"code": "4821"` (4 цифры). Показывать крупно («Код подтверждения»).
  В боте кнопки — три кода (верный + два случайных) и «Отклонить»; код в тексте сообщения **не** показывается,
  выбор неверного кода сразу отклоняет вход (`poll` → `denied`). Бот показывает устройство, платформу, IP и время.
  Ссылку входа может подтвердить только аккаунт Telegram, который открыл её первым.
- `POST /api/auth/poll` → новый статус `{"status":"too_many_devices","message":"…"}` (уже 20 устройств): nonce не
  тратится — после выхода на старом устройстве тот же опрос в пределах 5 минут вернёт `ok`. Устройство, не
  появлявшееся 90 дней, удаляется и не считается. Вытеснения больше нет — только отказ.
- Виджет: `auth_date` не старше **5 минут**; повтор тех же данных → `401 unauthorized` («уже использованы»);
  лимит устройств → `409 too_many_devices`.
- 401 для Bearer: `error` = `revoked` (токен отозван/неизвестен) или `token_expired` (90 дней без входа);
  испорченный заголовок/initData — `unauthorized`. На всё — экран входа.
- «Выйти на всех устройствах»: `POST /api/auth/logout {"all": true}` → `{"ok":true,"revoked":n}` — отзывает все
  токены пользователя, включая текущий; отдельные `revoke` не нужны. Есть и `POST /api/devices/revoke-all`;
  в боте `/devices` — кнопка «🚪 Выйти на всех устройствах».
- Service worker: `GET /app/sw.js` (файл `static/sw.js`, `text/javascript`, `Cache-Control: no-cache`,
  `Service-Worker-Allowed: /app/`) и `GET /app/manifest.webmanifest` (`application/manifest+json`, no-cache).
- Обложки: `/api/cover/{id}?u=&s=&e=<exp>` — подпись теперь со сроком (24 ч, вверх до часа). Ссылки без `e`
  или с истёкшим сроком → 404; клиент обновляет их тем же `GET /api/tracks?ids=` (обложка там тоже свежая).
  Поток: срок 12 ч (вверх до часа), продлевать так же.
- Лимит входов: 10 за 10 минут на IP (IPv6 — на сеть /64) и 300 за 10 минут на сервер; `X-Forwarded-For` —
  только от `TRUSTED_PROXIES` (по умолчанию частные сети); если вся цепочка — прокси, берётся адрес соединения.
- Загрузки:
  - одновременно не больше 2 запросов `/api/upload` на пользователя и 4 на сервер → `429 busy`;
  - очередь пользователя ≤ `UPLOAD_USER_QUOTA_GB` (10 ГБ) → `quota`;
  - свободное место перепроверяется каждые 64 МБ → `507 disk_full`;
  - 60 с без данных → `408 timeout`;
  - слишком большой файл / квота / диск / > 50 файлов: ответ **сразу** (413/507/429) с
    `{"uploads":[уже принятые], "rejected":[…], "error", "message"}` и `Connection: close` — остаток тела не
    читается (клиент может увидеть обрыв соединения; уже принятые файлы в очереди, см. `GET /api/uploads`);
  - принимаются только контейнеры mp3/flac/ogg/wav/mp4(m4a)/matroska(webm)/aiff/asf/aac, остальное → `failed`;
  - в `note` неудачи — общий текст («не удалось обработать файл»), подробности только в логе сервера;
  - «получаю» дольше часа → `failed`;
  - теги загруженного файла всегда переписываются по найденным метаданным (свои ID3/APEv2 и картинки
    удаляются); такой трек помечен `source=upload`, и если позже его скачают из обычного источника, файл в
    кэше заменяется скачанным (у всех пользователей).
- Поиск при входе по Bearer без привязанного Telegram — результаты привязаны к логину.

## Массовые операции и плейлисты из каталога
- **Скачать сразу в плейлист**: `POST /api/download` (поиск и страницы каталога альбом/исполнитель — тот же
  эндпоинт, тот же `token`) принимает необязательный `"playlist_id"`. Нужно быть владельцем или участником, иначе
  `404 playlist_not_found`. Ответ — дополнительно `"playlist": {"id","name","added_now"}`. Треки, которые уже есть
  в медиатеке, добавляются сразу (`added_now`); остальные — по мере загрузки. Порядок — как в выбранном списке,
  блок встаёт **в конец** плейлиста (после уже имеющихся). Неудавшиеся загрузки просто пропускаются.
- **Новый плейлист из поиска/каталога**: `POST /api/playlists {"name", …, "catalog": {"token","kind","i"?,"j"?,"idx"?}}` —
  `catalog` в том же формате, что тело `/api/download` (`kind`: `track` / `all` / `album` / `tracks` / `album_track`).
  Ответ — краткий плейлист + `"queued"` (сколько поставлено в загрузку) и `"added_now"`. Ошибки каталога
  (`404 expired`, `400 bad_kind|bad_index|bad_catalog`) — плейлист **не** создаётся.
- **Удалить из медиатеки пачкой**: `POST /api/library/delete {"track_ids":[…]}` (1–500) →
  `{"deleted": n, "skipped": m, "deleted_ids": […], "gone_ids": […]}` (чужие/несуществующие/повторы — в
  `skipped`). Трек, которого не осталось ни в одной медиатеке, удаляется с диска и из всех плейлистов.
  `deleted_ids` — удалённые из медиатеки (убрать из списков и страниц медиатеки); `gone_ids` — их подмножество,
  недоступное пользователю совсем (файл удалён или трека нет ни в одном его плейлисте, поток отвечает 404) — убрать
  из очереди. Остальные из `deleted_ids` (есть в чужой медиатеке) играют дальше из плейлистов (`owned: false`).
  Одиночное `POST /api/delete {"track_id"}` → `{"ok": true, "text", "track_id", "gone": bool}` — то же для одного трека.
- **Убрать из плейлиста пачкой**: `POST /api/playlists/{id}/remove {"item_ids":[…]}` — до 5000 за раз, одна
  транзакция.
- **Добавить пачкой**: `POST /api/playlists/{id}/add {"track_ids":[…]}` — до 5000 (как и раньше).
- **Перенести выделение**: `POST /api/playlists/{id}/move-many {"item_ids":[…], "to": index}` — выбранные позиции
  блоком (в их текущем порядке) на индекс `to` среди остальных (0 — в начало, больше длины — в конец) →
  `{"ok":true,"moved":n}`; ни одной из этого плейлиста → `404`, неверное тело → `400 bad_move`.
- Всё это работает одинаково с initData (Mini App) и `Authorization: Bearer` (PWA/приложения).
- Зеркало плейлиста в Jellyfin — без ограничения 500: создаётся с первыми 500 треками, остальные дописываются
  пачками по 100 (`POST /Playlists/{id}/Items`); если Jellyfin не даёт дописывать — пересоздаётся одним запросом.

## Сортировка и жанры медиатеки
- **Данные**: у трека появились `genre` (основной жанр), `genres` (все, внутри сервера) и `year`. Новые загрузки
  получают их из MusicBrainz/iTunes/тегов файла. Уже скачанные треки дозаполняются в фоне: один раз из тегов файлов
  (TCON/TDRC), потом — для оставшихся без жанра — iTunes, не больше 60 запросов в час. Названия жанров
  нормализуются: «rock; pop» → `Rock`, `Pop`; `EDM`, `R&B`, `Hip-Hop`, `Drum & Bass`; русские — «Русский рок».
- **JSON трека** (везде, где он отдаётся): дополнительно `"genre": "Rock"|null`, `"year": 1988|null`,
  `"added_at": <unix>|null` (когда трек появился в медиатеке пользователя; известно в списках медиатеки и
  в `/api/library/play`, в плейлистах/`/api/tracks` — `null`).
- **`GET /api/library`**: `q` (поиск по исполнителю, названию, альбому; без регистра, ё = е), `genre` (точное имя
  жанра без учёта регистра; трек подходит, если это любой из его жанров), `sort` =
  `added|title|artist|album|genre|year|duration|random`, `order` = `asc|desc`, `offset`, `limit` (≤ 500, по
  умолчанию 50), `seed` (для `random`: одно значение — один порядок, нужно для подгрузки страниц).
  Ответ: `{"total": <после фильтра>, "library_total": <вся медиатека>, "offset", "limit", "sort", "items": [трек…]}`.
  ⚠️ `total` теперь — число найденных (для пагинации), размер медиатеки — `library_total`.
  По умолчанию: `sort=added`. Направление по умолчанию: `added`, `year` — по убыванию, остальные — по возрастанию.
  Пустые значения (нет жанра/года/альбома/длительности) всегда в конце. При равенстве — исполнитель (без
  «The »), альбом, порядок файлов. `artist` — исполнитель → альбом → номер трека. Неверные `sort`/`order` → 400.
- **`GET /api/library/genres`** → `{"items": [{"name","count"}]}` — жанры медиатеки пользователя, частые первыми
  (трек считается в каждом своём жанре; треки без жанра не входят).
- **`GET /api/library/artists`, `/albums`**: `genre` (фильтр), `sort` = `name|count|added|year`, `order`.
  По умолчанию `name` по возрастанию (у альбомов — исполнитель, затем альбом), `count`/`added`/`year` — по
  убыванию. В элементах дополнительно `"year"` (самый поздний год треков, `null` если неизвестен) и
  `"added_at"` (последнее добавление).
- **`GET /api/library/play`**: те же `q`, `genre`, `sort`, `order`, `seed` + `limit` (≤ 3000) — «Слушать» и
  «Перемешать» (`sort=random`) по текущему виду. По умолчанию `sort=artist`. Старые `order=shuffle|artist|recent`
  (без `sort`) по-прежнему работают.

## Импорт списков TXT/CSV из Mini App (бэкенд)
- **`POST /api/import/file`** — `multipart/form-data`, поле **`file`** (одно; остальные поля пропускаются).
  Расширения `.txt` / `.csv` / `.tsv`, до 2 МБ; кодировка UTF-8 (с BOM или без), cp1251, UTF-16 с BOM.
  Форматы — как у файла, отправленного боту: CSV Tune My Music / Exportify / свои таблицы (колонки названия и
  исполнителя ищутся по заголовку, разделители `,` `;` таб `|`), TXT — строка на трек «Артист - Песня» (порядок
  «Песня - Артист» определяется сам), до 10 000 уникальных строк. Импорт сразу запускается (без шага
  подтверждения, как кнопка «Начать импорт» у бота), создаётся плейлист с именем файла без расширения («X (2)»,
  если занято); прогресс приходит и в чат с ботом.
  Ответ `200`: `{"import_id": int, "format": str, "total": int, "name": str, "playlist": {"id","name"}|null}` —
  `format` для показа («CSV», «TXT «Артист - Песня»», с хвостом «, повторяющихся строк пропущено: N»), `total` —
  треков в импорте, `name` — имя импорта (файл без расширения), `playlist` — `null`, если плейлист не создан (лимит).
  Ошибки (`{"error", "message"}`, `message` — по-русски, можно показывать как есть):
  `400 bad_multipart` / `no_file` (нет поля `file` с файлом) / `empty` (пустой файл) / `bad_format` (в CSV нет
  колонок названия и исполнителя) / `no_tracks` (ни одного трека) / `bad_file`; `413 too_large`;
  `415 unsupported` (не .txt/.csv/.tsv); `408 timeout`.
- Новый импорт виден в **`GET /api/import`** (`imports[]`: `id`, `filename`, `total`, `state`, `counts`, `text`);
  пауза/продолжение/отмена — существующие `/api/import/pause|resume|cancel`.
- **`POST /api/upload`** со списком (`.txt/.csv/.tsv`): файл не принимается как аудио, в `rejected` —
  `{"name", "error": "use_import", "message"}`. Если других файлов в запросе нет — ответ `415`
  `{"uploads": [], "rejected": […], "error": "use_import", "message"}`; клиенту — отправить файл в
  `/api/import/file`.

## Перекачка трека, сортировка плейлистов, источник действий (бэкенд, 2026-10-23)
- **`POST /api/tracks/{id}/redownload`** (тело не нужно) — «Перекачать трек» из своей медиатеки. Файл трека
  помечается проблемным (из общего кэша его больше не выдают другим), трек ищется и качается заново; новый файл
  проверяется (в т.ч. длительность против каталога) и атомарно заменяет старый **у всех**, у кого трек есть
  (медиатеки, плейлисты, раздача): теги, длительность, громкость (пересчёт в фоне), обложка. Не нашлось подходящего —
  старый файл остаётся, пометка «проблемный» тоже.
  Ответ `200`: `{"ok": true, "text": "🔁 Перекачиваю: A — T. …", "job": {"title": "Перекачать: A — T",
  "track_id": id}}`. Ход и итог — в `GET /api/activity` (`log`: «🔁 Файл заменён: …» или «❌ Не удалось
  перекачать: … — старый файл оставлен»). Ошибки: `404 not_found` (нет в своей медиатеке), `409 busy` (этот трек
  уже перекачивается), `429 rate_limited` (больше 10 в час) или квота очереди (`429 quota` / `507 disk_full`).
- В объекте трека (медиатека, плейлисты, `/api/tracks`) новое поле **`broken`**: `true` — файл помечен проблемным
  (перекачка идёт или не удалась). Повторное добавление такого трека сначала качает его заново, а файл из кэша —
  только запасной.
- **`GET /api/playlists/{id}?sort=&order=&seed=`** — `sort`: `manual` (по умолчанию, порядок плейлиста),
  `added` (когда добавлен в плейлист; по умолчанию новые первыми), `title`, `artist`, `album`, `genre`, `year`,
  `duration`, `random` (+`seed`); `order`: `asc` / `desc` (по умолчанию как у `/api/library`). Пустые значения —
  в конце. В ответе — `"sort"`. `item_id` у треков остаётся (удаление/перенос работают по нему), но перетаскивание
  имеет смысл только в `manual`. Неизвестный `sort` / `order` — `400 bad_sort` / `bad_order`.
- **Источник действий.** Вход по токену устройства (приложения, браузер) — действия «из приложения»: бот **не пишет**
  в Telegram о ходе импорта (`POST /api/import/file`), о загрузках файлов (итоги, «не опознан» — ответ через форму
  `need_info` в приложении) — всё видно через `GET /api/import`, `GET /api/uploads`, `GET /api/activity`.
  Mini App внутри Telegram (initData) и сам бот — как раньше (сообщения в чат). Telegram для приложений остаётся
  только для входа (код/подтверждение). Загрузки по ссылкам/поиску из веб-интерфейса в чат не писали и раньше.

## Поля для нативного Android 2.0 (бэкенд, 2026-10-24; только добавлены)
- Объект трека (медиатека, плейлисты, альбом/исполнитель, `/api/tracks`, загрузки): **`artist_key`**,
  **`album_key`** — папки трека, те же ключи, что принимают `GET /api/library/artist?a=` и
  `GET /api/library/album?a=&b=` («К исполнителю» / «К альбому»; у чужого трека из плейлиста страница ответит 404 —
  его нет в своей медиатеке); **`size`** — размер файла в байтах (`null`, если файла нет).
- **`GET /api/wave/now`**: уже отдаёт `title`, `artist`, `album`, `duration`, `started_at`, `cover` (подписанная
  ссылка обложки, `null` — нет обложки или трек не из своей медиатеки); добавлено **`track_id`** (`null` — не
  удалось сопоставить файл эфира с треком).
- **`GET /api/activity`**: `active` (строки «Исполнитель — Название») — без изменений; добавлено
  **`active_items`**: `[{"text", "artist", "title", "track_id", "progress"}]` — то, что качается сейчас;
  `track_id` известен только у перекачки (иначе `null`), `progress` — последний шаг («Soulseek: …», `null` — ещё нет).

## Обновления
Автообновление приложений Windows/Android идёт из **выпусков GitHub** репозитория (по умолчанию
`iKriu/pimusic-server`; в форке — `plugins.updater.endpoints` в `apps/windows/src-tauri/tauri.conf.json` и
`ServerUrl.UPDATE_REPO` в Android). К каждому выпуску прикладываются установщик, APK и два манифеста, которые
пишет `apps/build/release-manifests.sh`; приложения читают манифест последнего выпуска:
`https://github.com/<репозиторий>/releases/latest/download/{latest,android}.json`.

Каталог `/updates/` бэкенда (`$DATA_DIR/updates`, `GET /updates/<имя>` без авторизации) остаётся для тех, кто
раздаёт обновления со своего сервера своими сборками: имена — только плоские файлы `[A-Za-z0-9._-]+`, `latest.json` и
`android.json` — `Cache-Control: no-cache`, остальное — `public, max-age=86400`, `Content-Length` обязателен.

### `windows-native.json` — нативный клиент Windows (с 1.1.0)
```json
{
  "version": "1.1.0",
  "url": "https://github.com/<репозиторий>/releases/download/v1.1.0/PiMusic-1.1.0-setup.exe",
  "sha256": "<64 hex>",
  "size": 80000000,
  "notes": "Что нового",
  "pub_date": "2026-10-29T08:00:00Z"
}
```
- Рядом — `windows-native.json.sig`: base64 от 64 байт подписи ed25519 над **точными байтами** манифеста. Без верной
  подписи (ключ — `ManifestPublicKey` в `Update/Updater.cs`) обновление не предлагается. Пишет оба файла
  `apps/build/release-windows-native.sh`.
- `url` — только `https://github.com/<репозиторий>/releases/download/…`; перенаправления — только на хосты загрузок
  GitHub. Установщик сверяется по `sha256` и `size`, запускается с `/SILENT` и сам перезапускает приложение.
- Своя раздача через `/updates/` бэкенда: манифест и его подпись отдаются с `Cache-Control: no-cache`.

### `latest.json` — Windows (формат tauri-plugin-updater v2)
```json
{
  "version": "1.0.1",
  "notes": "Что нового (текст, можно с переводами строк)",
  "pub_date": "2026-11-01T10:00:00Z",
  "platforms": {
    "windows-x86_64":      { "url": "https://github.com/<репозиторий>/releases/download/v1.0.1/PiMusic_1.0.1_x64-setup.exe", "signature": "<содержимое .sig>" },
    "windows-x86_64-nsis": { "url": "https://github.com/<репозиторий>/releases/download/v1.0.1/PiMusic_1.0.1_x64-setup.exe", "signature": "<содержимое .sig>" }
  }
}
```
- `version` — semver; обновление предлагается, если больше установленной. `signature` — подпись minisign установщика
  (`PiMusic_<v>_x64-setup.exe.sig`, ключ `<каталог сборки>/keys/updater.key`), проверяется по `pubkey` из
  `tauri.conf.json`.
- Приложение: проверка через минуту после запуска, затем каждые 6 ч и по пункту трея «Проверить обновления»;
  установка — NSIS `passive`, приложение закрывается и запускается снова.

### `android.json` — Android
```json
{
  "versionCode": 10001,
  "versionName": "1.0.1",
  "url": "https://github.com/<репозиторий>/releases/download/v1.0.1/PiMusic-1.0.1.apk",
  "sha256": "<64 hex, нижний регистр>",
  "size": 6543210,
  "notes": "Что нового",
  "pub_date": "2026-11-01T10:00:00Z"
}
```
- Обязательны `versionCode` (int, `major*10000 + minor*100 + patch`), `url`, `sha256`; `versionName`, `notes`,
  `size`, `pub_date` — по желанию. `url` — только `https://github.com/<репозиторий>/releases/download/…` (иначе
  приложение игнорирует манифест). GitHub отдаёт файлы перенаправлением на своё хранилище: приложение идёт по
  перенаправлениям само и пускает только `github.com`, `objects.githubusercontent.com`,
  `release-assets.githubusercontent.com` по https.
- Приложение: при запуске, не чаще раза в сутки; если `versionCode` больше установленного — диалог M3, загрузка
  APK в кэш, сверка sha256, установка через PackageInstaller (APK подписан тем же ключом, что установленный).

### Мост `PiMusicNative` (Windows, `features.updates === true`) — для диалога обновления в веб-интерфейсе
Системный диалог Windows не в стиле M3, поэтому веб-приложение может показывать свой. Не подписалось — оболочка
показывает системный диалог (как сейчас).
- `N.on("update", fn)` — первая подписка сообщает оболочке (`setUpdateUi {enabled:true}`), что диалог рисует
  веб-интерфейс; отписка последнего слушателя — `enabled:false`; при каждой загрузке страницы флаг сбрасывается.
  Событие приходит, когда фоновая или ручная (трей) проверка нашла версию и окно на экране:
  `{available: true, version: "1.0.4", currentVersion: "1.0.3", notes: "…", date: <unix>|null, manual: bool}`.
  Если окно скрыто в трей — системный диалог.
- `await N.checkUpdate()` — проверить сейчас (кнопка «Проверить обновления» в Настройках): то же
  `{available: true, …}` или `{available: false, currentVersion}`; `{available: true, installing: true}` — уже
  ставится; ошибка сети/подписи — reject с текстом. Найденная версия запоминается для `installUpdate`.
- `await N.installUpdate()` → `{started: true}`; дальше события `updateProgress` `{downloaded, total|null,
  percent|null}` (не чаще раза на процент) и при ошибке `updateError` `{message}`. При успехе установщик закрывает
  приложение — веб-интерфейсу ничего делать не нужно (можно показать «Устанавливается…»). Без найденного
  обновления — reject.
- `await N.dismissUpdate()` — «Позже»: фоновая проверка больше не спрашивает про эту версию до перезапуска.
- Тексты (русские) — на стороне веб-интерфейса: «Доступна версия X», «Установлена Y», «Что нового», кнопки
  «Обновить» / «Позже», «Загрузка… N %», «PiMusic закроется на время установки и запустится снова».
- Android: диалог нативный (MaterialAlertDialogBuilder, схема M3 из seed #F5A524), методов моста нет.

## Кэш и офлайн (Windows)
С **Windows 2.0** интерфейс (копия `bot/app/static`, собирается в приложение при сборке) лежит **внутри приложения**:
страница — `http://tauri.localhost/index.html` (статика — `http://tauri.localhost/static/…`), с сервера — только API,
обложки и поток. Страницы сервера в окно не загружаются (ссылки на них открываются в браузере).

### Адрес API (фронтенд)
- Оболочка до загрузки модулей задаёт `window.PIMUSIC_API_BASE = "https://music.example.com"` — **origin** настроенного
  сервера (scheme://host[:port], без `/app/` и без `/` в конце); то же — `PiMusicNative.apiBase`. В браузере, Telegram
  и Android не задан → как сейчас, относительные адреса.
- Все запросы: `fetch(PIMUSIC_API_BASE + "/api" + path)`, `credentials: "omit"` (авторизация — только
  `Authorization: Bearer`, cookie не нужны); загрузка файлов (XHR `/api/upload`) — тоже с базой.
- Относительные ссылки из ответов API (`/api/stream/…`, `/api/cover/…` и т. п.) — с префиксом базы везде, где они
  идут в `<img>`, `<audio>`, `fetch`. Обложки для извлечения цвета (canvas) — `crossOrigin = "anonymous"`.
- `location.origin` больше не сервер: ссылки «Сервер: …» в Настройках — из `PiMusicNative.serverUrl`; ссылки для
  шаринга — из ответов API (`app_link`) или `PIMUSIC_API_BASE + "/app/…"`.
- Смена сервера (`openServerSettings()` → страница выбора) перезапускает приложение (CSP и каталог кэша зависят от
  сервера). `features.cache`, `features.offline` = true, `PiMusicNative.localUi === true` (через
  `__PIMUSIC_NATIVE_CONFIG__.localUi`).
- `features.fileDrop === true` — перетаскивание файлов работает как в браузере (обработчик drag&drop Tauri
  выключен, `disable_drag_drop_handler`): `dragover`/`drop` с `dataTransfer.files` доходят до страницы, DnD в
  «Загрузках» можно показывать. Нет флага (оболочка 1.x) — DnD в окне не работает, оставлять только выбор файлов.

### Воспроизведение через кэш
- Протокол оболочки `http://pimusic.localhost` (Rust, `apps/windows/src-tauri/src/cache.rs`).
- `<audio>.src = PiMusicNative.cacheUrl(trackId, streamUrl)` →
  `http://pimusic.localhost/stream/<trackId>?src=<абсолютный подписанный URL /api/stream/…>`.
  - трек есть на диске целиком (офлайн или кэш потока) — отдаётся с диска (Range/206), сеть не нужна;
  - нет — оболочка сразу начинает качать **полный файл** в кэш потока и отдаёт уже скачанное по мере загрузки
    (Range/206); перемотка далеко вперёд недокачанного — диапазоном прямо с сервера;
  - ответы с `Access-Control-Allow-Origin: *` — можно `crossOrigin = "anonymous"` для Web Audio (эквалайзер).
- Следующий трек: `await N.cachePrefetch(trackId, streamUrl)` (при старте текущего) → `{trackId, cached}`;
  качает полный файл в фоне, повтор безопасен.
- `src` должен вести на настроенный сервер (иначе 403). `trackId` — `[A-Za-z0-9_-]{1,64}` (число тоже можно).
- Кэш потока — LRU по времени последнего воспроизведения, лимит по умолчанию **1 ГиБ**; файлы, отданные за последние
  15 мин, и качающиеся не вытесняются. Офлайн-треки в лимит не входят и лежат до удаления.
- Каталог: `%LOCALAPPDATA%\io.github.ikriu.pimusic\media\<origin сервера>\{stream,offline}` (`.bin` + `.json`).

### Методы моста (все → Promise; ошибки — reject с русским текстом)
| Метод | Аргументы | Ответ |
|---|---|---|
| `cacheUrl(trackId, streamUrl)` | синхронный | строка для `<audio>.src` (без кэша — `streamUrl` как есть) |
| `cachePrefetch(trackId, streamUrl)` | | `{trackId, cached}` — `cached: true`, если файл уже есть |
| `cacheStatus(trackId)` | | `{trackId, offline, cached, downloading, downloaded, total}` |
| `offlineDownload(trackId, streamUrl, meta)` | `meta` — любой JSON (название, исполнитель, обложка…) | `{trackId, started, offline}` |
| `offlineList()` | | `{items: [{trackId, size, contentType, addedAt, meta}]}` — новые первыми |
| `offlineDelete(trackId)` / `offlineDelete("all")` | | `{deleted}` (качающийся — отменяется) |
| `cacheInfo()` | | `{offline: {count, bytes}, stream: {count, bytes, limit}, dir}` |
| `cacheClear()` | | очистить кэш потока (офлайн не трогает) |
| `setCacheLimit(bytes)` | ≥ 256 МиБ | `{limit}`; лишнее вытесняется сразу |

Низкоуровнево — `N.call("offlineDownload", {trackId, url, meta})` и т. д. (`url` — абсолютный).
События (`N.on(name, fn)` / `pimusic-native:<name>`):
- `offlineProgress` `{trackId, downloaded, total|null}` — не чаще чем раз в 1 МиБ;
- `offlineDone` `{trackId, size}`; `offlineError` `{trackId, message}` (в т. ч. «отменено»).
Офлайн-трек из кэша потока копируется без сети. Подписанный `streamUrl` нужен только на время загрузки — потом
трек играет по `cacheUrl(trackId, любой_или_старый_url)` с диска.

### Что нужно от бэкенда (Windows 2.0)
- CORS для `/api/*` с Origin **`http://tauri.localhost`** (уже в `DEFAULT_CORS_ORIGINS`), заголовки `Authorization`,
  `Content-Type`, `Range` (есть), `Access-Control-Expose-Headers` с `Content-Range, Accept-Ranges, Content-Length`
  (есть). Cookie/`Allow-Credentials` не нужны. Проверить, что CORS-заголовки есть у **всех** ответов `/api/*`, включая
  401/404 JSON, `FileResponse` потока и обложек, загрузку файлов (preflight `POST` с `Authorization`), — middleware
  добавляет их только до `prepare()`.
- `/api/stream/{id}`: `Content-Length` у полного ответа (по нему кэш отдаёт трек, не дожидаясь конца загрузки),
  `Range`/206 (перемотка недокачанного), без перенаправлений. Сейчас так и есть (`FileResponse`).
- Срок подписи ссылок потока — не меньше длительности загрузки трека (сейчас достаточно).

## Тексты песен: перезапрос и проверка; CORS у потока «Моей Волны» (бэкенд, 2026-10-27)
- **`POST /api/tracks/{id}/lyrics/refetch`** — «Найти текст заново» (неверный или сбитый текст). Доступ — как у потока
  (`track_access`: своя медиатека или доступный плейлист). Тело необязательно: `{"clear": true}` — если нового текста
  нет, удалить текущий (только для трека из своей медиатеки — файлы текста общие у всех держателей). Ищет по новым правилам и пишет результат везде: USLT/SYLT в MP3, `.lrc`/`.txt` в общем кэше
  и в медиатеках пользователей (жёсткие ссылки), Jellyfin перечитает при ближайшем сканировании.
  Ответ `200` — как у `GET /api/lyrics/{id}` плюс `status`: `updated` (найден и записан новый) | `same` (найден
  тот же) | `cleared` (нового нет, старый удалён: `clear` или старый точно чужой/сбит) | `not_found` (лучшего нет,
  старый оставлен; исправный синхронный текст на обычный не меняется). Ошибки: `404 not_found`, `409 busy` (текст
  этого трека уже ищется), `429 rate_limited` (20 запросов в час на пользователя), `504 timeout` (сервисы текстов
  недоступны или не ответили за 100 с — ничего не изменено).
- **Правила подбора** (`lyrics.fetch`): LRCLIB `get` по исходному названию и альбому → `get` по очищенному названию
  (без «(Eurovision 2018 - Israel)», «- 2011 Remaster», «(Live)», «[Ремикс]», feat.) → LRCLIB `search` (тот же
  исполнитель, похожее название, длина ±5 с) → syncedlyrics (только синхронный текст и только при известной
  длительности; его «обычный» текст не берётся — его не проверить). Синхронный текст бракуется, если последняя
  метка позже конца трека больше чем на 15 с, текст кончается раньше половины трека или строки по всей песне идут
  «пачками» чаще 0.8 с (> 30 % промежутков; «пачка» в самом конце — частый дефект LRCLIB — допускается).
  Служебные строки NetEase (`作词 :`, `作曲 :` …) вырезаются. Лучше без текста, чем чужой.
- **Разовая проверка всего кэша**: `podman exec pimusic-bot python -m app lyrics-check` — сухой прогон, печатает
  подозрительные синхронные тексты; `--apply` — перезапросить их и записать найденное (не нашлось — точно чужой/сбитый
  текст удаляется, «кончается до середины» остаётся; при сбое сети ничего не трогается); `--all` — перезапросить все
  треки (долго, LRCLIB ~3 запроса/с); `--limit N`.
- **`/stream/{login}/{token}.mp3`** («Моя Волна») теперь отдаёт CORS-заголовки для Origin нативных оболочек
  (как `/api/*`): интерфейс Windows 2.0 (`http://tauri.localhost`) ставит `<audio crossorigin="anonymous">`, и без
  `Access-Control-Allow-Origin` WebView2 обрывал поток сразу — клиент 5 раз переподключался и показывал «Поток
  „Моей Волны“ сейчас недоступен». В журнал бота пишутся подключения/отключения слушателей и причина.
